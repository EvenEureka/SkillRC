skillrc-gate

Should this agent change ship? A release check that answers from the run logs.

Code Docs Full technical report

The problem

Teams that build LLM agents change them all the time: they add a memory of lessons from past runs, rewrite the prompt, or switch on a new feature. Before each release someone has to decide whether the new version is actually better. The usual method is to run both versions on a test set and compare the average score. That method fails in predictable ways:

  • Luck. A small difference can come from which tasks happened to be in the test set.
  • Bundling. When two changes ship together, a good one can hide a bad one.
  • Unfair comparison. Something else changed between the two runs: the model version, a setting, the task list.
  • Dropped failures. Tasks that crashed are quietly left out, which shifts the average.
  • Hidden cost. The score holds, but every task now uses far more tokens or time.

A real case: a good release hid a bad change

In our SkillRC project, a shopping agent (Qwen3-8B on the WebShop benchmark, 500 tasks) received two changes at once: a short label that tells it which page it is on, and a memory of 30 lessons distilled from earlier runs. Together they raised the average task score (0 to 1) by +0.132, so the release looked good. Tested one at a time, the label was worth +0.251 and the memory −0.119. The memory made the agent worse, and the average hid it.

What skillrc-gate does

You give it the logs of the old and the new version on the same tasks, plus a short file that names each change. For every change separately, it answers with one of these:

PASS shipBLOCK don't ship
INCONCLUSIVE not enough evidence, not approvedINVALID experiment broken

It is a command-line tool, and its exit code is the answer, so a CI pipeline can stop a release the way a failing unit test stops a merge. Before it answers, it checks four things:

  1. Same conditions. The two versions may differ only in the declared change. The model version, settings, task list and a fingerprint (hash) of every input file are compared; any other difference means "experiment broken".
  2. Nothing dropped. Every planned task needs a result. Crashed tasks are rerun and counted, never removed.
  3. Real or luck. It resamples the tasks thousands of times to find the range the true difference lies in. "Don't ship" needs the whole range to be worse than the allowed drop (here 0.05). "Ship" needs the whole range to be better than that. Anything in between is "not enough evidence".
  4. Cost. Tokens and time per task must stay within a limit (here +30%).

It also reports how the agent's behaviour changed and shows the runs of both versions on the same task side by side.

Tested on a real release decision

We then ran a fresh experiment and let the gate decide. The plan and the decision rules were written down and frozen before anything ran.

changewhat happenedverdict
Ship the memoryscore 0.57 → 0.44; tokens per task +58%BLOCK don't ship
Ship a "fixed" memory (six suspicious lessons replaced)score still 0.074 lower than with no memory; tokens per task +39%INCONCLUSIVE not enough evidence, not approved
Add six tips to the prompt (another benchmark, AgentDojo, run through the Inspect AI framework) score +0.026, too few tasks to tellINCONCLUSIVE not enough evidence, not approved

What we learned

  1. The memory makes the agent keep searching instead of buying. With the memory, the agent went back to the search page 0.82 times per task instead of 0.29, and ended 31% of tasks without buying anything instead of 18%. It also used 58% more tokens. The gate blocks it on both score and cost.
  2. Removing the obvious culprit did not fix it. Six of the 30 lessons tell the agent to keep searching. On 500 new tasks, replacing those six with neutral text of the same length stopped the extra searching (0.84 → 0.26 returns to search per task; 0.32 without any memory). But it won back only 0.036 of the 0.110 that the memory had cost, and that gain could be zero (95% range [−0.003, +0.075]). As a control, we also replaced three other, randomly chosen sets of six lessons. One of them won back more than our fix did (+0.119). So the data do not support "these six lessons caused the loss", and the gate does not approve the fixed memory.
  3. When the evidence is thin, it says so. On 96 AgentDojo tasks, only a score change of about 0.11 can be detected reliably; the tips changed the score by +0.026. The gate answers "not enough evidence" instead of guessing.

How it is built

  • Reads logs from the SkillRC agent runner, from the Inspect AI framework, or from a simple JSON-lines format.
  • The runner is built for long unattended GPU jobs: every attempt is logged before it starts, a crashed run resumes where it stopped, and each job checks that the previous one finished correctly before it starts.
  • The release experiment ran 6,500 agent episodes with 0 crashes and 0 missing results.
  • Every verdict on this page can be reproduced from the published logs: one script restores the logs, one command recomputes the report.
  • 94 automated tests; the decision rule was also checked on simulated data where the true answer is known.
  • One lesson: we ran every setting twice to measure run-to-run noise. Both runs gave identical results on all 2,500 task pairs (greedy decoding, seeded environment). In this setup the second run added nothing; more tasks would have been a better use of the GPUs.

Details and limits

Statistics, assumptions and review record
  • Ranges are 95% intervals from a paired bootstrap over tasks (20,000 resamples, stratified by product category, fixed seed). They describe the uncertainty from which tasks were sampled, given the runs we made; they do not cover future runs.
  • Cost checks: "don't ship" only if the limit is confirmed exceeded (Holm correction across the two cost checks); "ship" only if the whole range stays under the limit. The fixed memory's token increase was +38.5% with range [+29.8%, +48.1%], straddling the +30% limit, so its cost check was also "not enough evidence". Its score range was [−0.119, −0.029]: below zero, but not wholly below −0.05. With an allowed drop of 0.02 it would have been blocked.
  • The allowed drop (0.05) and the cost limit (+30%) are example policies fixed before the runs, not recommendations. In simulation, the chance of "ship" when the true change sat exactly at the allowed drop was 0.018–0.041, against a target of 0.025.
  • The "fix" replaces the six lessons with unrelated text of the same length, so it tests replacement, not deletion. The localization test required the fix to beat the original memory and each of the three random replacements; it failed for repair vs published memory; repair vs comparison edit 1; repair vs comparison edit 3. It covers those three replacements only.
  • Behaviour numbers (returns to search, tasks without a purchase) and the "won back" amounts for the random replacements are descriptive and not part of any verdict.
  • The two repeat runs matched in score, steps and tokens, not in latency; this does not prove determinism in other setups.
  • WebShop here is the 1,000-product version with generated shopping goals and a 15-step limit; most tasks are fashion items. The AgentDojo check used 96 tasks, two attempts each.
  • The bundled-release case comes from an older run without the provenance records the gate requires, so the gate shows its numbers without a decision (DESCRIPTIVE numbers only, no decision).
  • The design and implementation went through eleven rounds of review by an independent model reviewer (Codex) before launch: design, pre-registration and reviews, calibration, historical report, AgentDojo report.
