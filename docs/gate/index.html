The question

An agent team adds a distilled memory, edits a prompt, or turns on a harness feature. Before shipping: is the new version better or worse on a fixed task set, by how much, at what cost, and if it is worse, which part of the change is responsible? A single before-and-after number cannot answer that, especially when several changes ship together.

The gate reads the logs of both versions on the same tasks and returns one verdict per declared change: PASS BLOCK INCONCLUSIVE INVALID DESCRIPTIVE. The exit code is the verdict of the target selected with --target (or the spec's default target), so a CI job can stop a release.

What the gate found

  1. A bundled release hid a regression. On 500 WebShop sessions with Qwen3-8B, shipping a page label and a distilled memory together looked like a gain over the old release (Δ +0.132 [+0.089, +0.174]). Split into declared interventions, the label alone gave +0.251 and the memory, given the label, −0.119 [−0.164, −0.075] while adding +55% prompt tokens per episode. These logs predate the provenance contract, so the gate reports them as DESCRIPTIVE: real statistics, no release decision.
  2. Re-run under the contract, the memory is blocked. Fresh runs with full provenance, on the same 500 sessions and the same reader. With the published memory the agent scored 0.436; without it, 0.571 (Δ −0.134 [−0.176, −0.092]). The memory also added +58% prompt tokens per episode. The gate returns BLOCK on both the score and the cost limit. The logs show what changed: with the memory the agent went back to search 0.82 times per episode instead of 0.29, and ended 31% of episodes without buying anything instead of 18%.
  3. Fixing the visible symptom did not fix the regression. Six of the memory's 30 rules tell the agent to keep searching. On 500 held-out sessions, replacing those six with unrelated text of the same length cut the extra searching: returns to search per episode fell from 0.84 with the published memory to 0.26 (no memory: 0.32). The score gain over the published memory was small and uncertain: +0.036 [−0.003, +0.075]. One of three comparison edits, which replaced six other rules chosen by a fixed random draw, did better than the repair (−0.083 [−0.123, −0.043] for repair minus that edit). The localization criterion was set in advance: the repair must beat the published memory and each comparison edit. It is not met (not supported: repair vs published memory; repair vs comparison edit 1; repair vs comparison edit 3), so the logs do not support the explanation that these six rules cause the loss. The repaired memory still scores below no memory: Δ −0.074 [−0.119, −0.029], with +38.5% [+29.8%, +48.1%] prompt tokens. The score interval excludes zero but crosses the −0.05 boundary, and the token interval crosses its +30% limit; both checks are inconclusive, so the gate returns INCONCLUSIVE and the change does not get release approval. With a margin of 0.02 the score check would BLOCK.
  4. Not enough evidence is also a verdict. Through Inspect AI on 96 AgentDojo tasks (two epochs per arm), a block of six tips in the system prompt scored 0.427 vs 0.401 (Δ +0.026 [−0.047, +0.099]): the score passes the non-inferiority check, but the token cost (+21% [−2%, +59%]) and p95 latency (−15% [−43%, +53%]) could neither be shown under the +30% tolerance nor shown to exceed it. The gate returns INCONCLUSIVE and says why. With 96 tasks, the score change detectable with 80% power (two-sided α = 0.05, normal approximation from the observed paired variability) is about 0.11.

How it works

The gate does not run agents; it reads their logs (SkillRC runner, Inspect AI, or a plain JSONL schema). Each stage passes one thing to the next:

stagewhat it doespasses on
ingestparses each arm's logs into episodes and a run manifest; all runs of an arm must share one fingerprintarms (a broken arm fails only its own targets)
fingerprint checkthe two versions may differ only in the declared interventions and in execution metadata (GPU, host, ports, job and block ids); all other configuration, the model revision, the scorer, the scientific serving and environment settings, and every file hash must match; missing provenance means no release decisionundeclared differences (any → INVALID)
pairingbuilds the expected task × repetition grid from a frozen task registry, picks each cell's scored attempt, counts missing and failed cellstask-aligned table
statisticstask-clustered, stratified bootstrap; order-statistic intervals that agree exactly with the p-values; Holm across guardrails; missing cells bound the scoreestimates and intervals
verdictvalidity and provenance checks come first; a degenerate component is INCONCLUSIVE; otherwise BLOCK needs a score interval wholly below −δ or a Holm-confirmed cost violation, and PASS needs a score interval wholly above −δ, every guardrail passing and no missing cells; everything else is INCONCLUSIVEone verdict per change, with reasons
reportJSON for machines, Markdown for CI, HTML with behaviour shifts and paired replaysfiles and exit code

Engineering

The producer side is built for unattended GPU runs: every attempt is journaled before it starts; a run resumes only under the same fingerprint; interrupted or truncated records are recovered; a run stops itself after repeated infrastructure failures so its servers can be restarted; each job in a chain checks that its predecessors succeeded (hash-verified markers); state files are published atomically. The contract and its implementation went through eleven numbered rounds of review by an independent model reviewer (Codex) before launch (design, pre-registration and review record); 94 tests and a calibration study (calibration.md) back the decision rules.

The pre-registered runs: 6,500 episodes over 13 arm-runs, with 0 infrastructure failures and 0 missing cells. Each repeated arm ran its second repetition in a separate execution window hours later. Across these two windows, all 2500 of 2500 arm–task pairs (5 arms) matched on score, step count and prompt-token count (greedy decoding, prefix caching off, seeded environment). The score A/A contrast is therefore exactly zero, and the gate reports it as degenerate rather than as evidence of stability. This does not establish determinism for latency or for future runs, but here the second repetition added no score information; more tasks would have bought more precision.

Limits

WebShop here is the 1,000-product version with generated goals, fashion-heavy test panels and a 15-step budget; readers are open Qwen3 models. Intervals describe task-sampling uncertainty given the observed execution windows, not future windows. The error budget is nominal: in simulation, the chance of a PASS when the true change sits exactly at the margin was 0.018–0.041 against a nominal 0.025. The margin (0.05) and the cost tolerances (+30%) are illustrative policies fixed before the runs, not recommendations. Which rule caused a loss is tested only through declared ablation arms, never inferred automatically. The repair replaces the six rules with unrelated text of the same length, so it tests replacement, not deletion; the three comparison edits are the only alternatives the localization claim covers. Behaviour shifts (returns to search, episodes without a purchase) are descriptive, with no multiplicity adjustment, and are not part of any verdict.
